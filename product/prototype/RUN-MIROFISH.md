# General Learning: graph-based local travel study

Run commands from `product/prototype` in the cloned repository. Python 3.10+ runs the web server and recorded replay; the isolated engine environment uses Python 3.12.

## Open the demo

```sh
python3 server.py --port 8765
```

Open http://127.0.0.1:8765. The research stage shows the recorded MiroFish knowledge graph. Select a node to inspect its source anchor and relationships. The graph-derived population contains 1,000 distinct synthetic travel scenarios. A fresh run can use 50, 250, 350 or 1,000 respondents. Recorded replays make no model calls and are explicitly labelled.

The graph was extracted from two dated, linked research summaries, not from live browsing when you press Run. Profiles use five attitude seeds generated by MiroFish's profile generator and a fully crossed scenario design. The earlier rule-based app remains at `/legacy`.

## Install the local engine

Install Git, [uv](https://docs.astral.sh/uv/getting-started/installation/) and [Ollama](https://ollama.com/), then:

```sh
sh setup-mirofish.sh
ollama pull qwen3-coder:30b
```

Start the Ollama application, or run `ollama serve` separately if it is not already running. The model occupies approximately 18 GB on disk. Development used a 48 GB Mac; a clean second-machine installation has not been tested. Smaller machines need a smaller model and their own quality/performance benchmark.

The bundled graph works without rebuilding it. To regenerate entities, relationships and profile seeds through the actual MiroFish-local classes:

```sh
.mirofish/venv/bin/python graph_pipeline.py --repo .mirofish/repo --output .travel-graph
```

The graph command uses local Ollama. It stores the SQLite graph, model-call audit and generated population under ignored `.travel-graph/`. It rejects extraction items without an exact anchor in the supplied research summary and items outside the declared ontology. Source anchoring is a provenance check, not a guarantee that an inferred relationship is correct.

Optional paths `GL_MIROFISH_PYTHON` and `GL_MIROFISH_REPO` select an existing installation; `GL_LOCAL_MODEL` selects an installed Ollama model. No provider key is needed. The inference endpoint is fixed to localhost. The launcher does not forward saved provider credentials or telemetry configuration.

## What runs

Pinned community fork: [shayswrld/mirofish](https://github.com/shayswrld/mirofish), commit `8d4eea4dfa981ecd23c3b385953b4085dfd9b6ca`.

1. MiroFish `GraphBuilderService`, `LocalGraphExtractor` and `LocalGraphStore` extract and persist entities and edges in SQLite. The ontology is tailored to the study. Exact source anchors are retained; unsupported items are excluded and logged.
2. MiroFish `EntityReader` reads graph-connected attitude cohorts. `OasisProfileGenerator` uses graph context and a bounded travel-study prompt to generate attitude seeds, without inventing demographics or prescribing purchase choices.
3. General Learning constructs a transparent scenario design: 5 attitude seeds × 5 travel parties × 5 frequencies × 4 current alternatives × 2 planning-effort levels = 1,000 unique profiles. Equal allocation is a design choice, not an estimate of population proportions.
4. MiroFish `IPCHandler.handle_interview` executes OASIS `ManualAction(INTERVIEW)` for each respondent and reads the SQLite trace. Each agent has separate memory and one actual local model call. Four calls are queued at a time; Ollama controls hardware execution.
5. Structured answers are checked and synthetic time-value scenarios calculated in Python. Malformed answers and failed requests are counted separately. No fabricated or duplicated response fills a missing result.

The local fork replaces official MiroFish's Zep-backed graph with SQLite. This is not a claim to run Zep, autonomous live research or social diffusion rounds. The research knowledge graph and the OASIS agent graph are distinct structures.

## Scale, runtime and data

The 1,000-person job has technical checkpoints after the batches crossing 50 and 250 completions. Because batches contain four profiles, these can occur at 52 and 252 attempts. Fewer than 95% valid answers stops further scaling; untouched profiles remain explicitly unattempted. A technically successful checkpoint does not validate model realism or predictive accuracy. All-positive answers remain visible and flagged.

The initial checkpoint took about 138 seconds for 52 valid responses. Allow tens of minutes for 1,000 local responses; do not wait for live inference during a short video. Use the recorded replay after the job finishes. Each interview has a 150-second limit; the full job has a three-hour limit. Reloading the browser reconnects to an active job. Keep the server running until it finishes.

Actual inputs, prompts, response JSON, model usage, graph snapshot, log and SQLite interview traces are stored in `.travel-runs/<id>/`. Real feedback belongs only in these ignored local folders. The checked-in graph and recordings contain public research summaries and synthetic data, not private interviews or credentials.

## Feedback and validation

After a baseline completes, add feedback with its date, recruitment limits, response type, corresponding workflow and matching offer. The original run is preserved and a new audience version created. Only the selected profile receives the added workflow context; its reported choice is retained for comparison rather than directly supplied as the target answer. The selected population reruns with fresh memory. Unchanged profiles provide a comparison for stochastic variation.

The bundled teaching feedback is illustrative. No real interviews or separate validation data have been supplied. Matching feedback used during revision is not independent predictive validation. A larger synthetic sample does not fix systematic model bias, unsupported features or missing real-world evidence. No price is tested, so conditional interest is not willingness to pay a stated price. Time-value calculations are not revenue forecasts.
